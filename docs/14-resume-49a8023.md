# Reanudación exacta desde 0x049A8023

Fecha: 2026-09-24.

Este documento recupera exactamente el punto donde quedó interrumpido el análisis de cooperativo local sobre **BioRevHD 30-Enero-2013.exe** (SHA-256 `9124bb92d6c54a047ade47dacc8429221b18f9910b504f0e87718d5151013f69`).

## 1. 0x049A8023 no es lógica de pickup

Desensamblado directo del EXE original:

```asm
0x049A8012  push 0x10F0
0x049A8017  call 0x01C19D66
0x049A801C  push eax
0x049A801D  push 0x04D30838
0x049A8022  mov  ecx,0x05579584
0x049A8027  call 0x01C24491
```

La dirección `0x04D30838` contiene la cadena literal:

```text
uItem
```

Por tanto esta rutina inicializa el DTI global de `uItem` en `0x05579584`.

La función inmediatamente posterior, desde `0x049A8070`, empuja `0x04D30850`, que contiene:

```text
uItem::cNetSyncData::cGetItemSyncData
```

Así que el punto visible en el turno interrumpido pertenecía al registro global de tipos y no al handler que decide el destinatario del objeto.

## 2. El handler común de pickup conserva el actor

La rutina relevante es:

```text
0x024646F0
```

Recibe el actor por `[ebp+8]`. Tras los filtros iniciales conserva ese actor en `[ebp-0x14]`.

En las ramas de entrega se llama repetidamente:

```asm
mov ecx,[ebp-0x14]
call 0x01BCC327
```

El thunk `0x01BCC327` salta a `0x01D336A0`.

Implementación real:

```asm
0x01D336C3  mov ecx,[ebp-8]
0x01D336C6  add ecx,0x1524
0x01D336CC  call 0x01C120B1
```

Por tanto la ruta es literalmente:

```text
actor uNpc*
 -> actor + 0x1524
 -> cBioItemPack del propio actor
```

## 3. Conclusión cerrada en este punto

La entrega de objetos no está hardcodeada al inventario de P1.

Una vez que un actor válido llega al handler común, el objeto se procesa contra el `cBioItemPack` perteneciente a ese actor. Esto es coherente con el trabajo previo donde las acciones PcsSub de armas/slots ya terminaban sobre el pack del `uNpc` partner.

Por tanto, para cooperativo local, el bloqueo de Sub0 debe buscarse antes de esa entrega:

1. selección del actor local candidato;
2. filtro de categoría `pl`;
3. input/ActionCommand que confirma la interacción.

No se debe crear un inventario paralelo artificial para P2.

## Siguiente bloque

Seguir exactamente desde el gate inicial de `0x024646F0`:

```asm
actor -> getCharaID
      -> 0x01C8C9A1
```

y demostrar qué categoría acepta stock y si Sub0, que sigue siendo `np`, queda rechazado ahí.

Después, separar esa entrega principal de la regla secundaria de munición cooperativa en `0x027ABFE0`.


## 4. El gate stock de pickup es exclusivamente `pl`

En `0x024646F0`, antes de cualquier entrega al pack:

```asm
0x0246471D  mov  ecx,[ebp+8]     ; actor
0x02464720  call 0x01C53859      ; charaID
0x02464725  push eax
0x02464726  call 0x01C8C9A1
...
0x02464733  je   0x024649AE      ; rechaza si false
```

`0x01C8C9A1` es un thunk a `0x01D77EB0`.

La implementación real hace:

```asm
push id
call 0x01C1C8B8   ; thunk -> normalizador 0x01D4B120
cmp  eax,0x80010000
sete al
```

El normalizador `0x01D4B120` aplica:

```asm
and eax,0xF00F0000
```

Por tanto el gate acepta exactamente categoría:

```text
0x80010000 = pl
```

y rechaza a Sub0, que permanece en categoría:

```text
0x80020000 = np
```

aunque su ThinkMode haya pasado de Cpu a Pad.

Conclusión: el primer bloqueo concreto de pickup local P2 está demostrado en el filtro de categoría; no está en `cBioItemPack`.

## 5. La regla secundaria de munición Coop es independiente del pickup principal

Al final del mismo handler, el item se clasifica mediante:

```text
0x01C78FA0 -> 0x01D754A0
```

La implementación compara el grupo normalizado con:

```text
0x80040200
```

Cuando coincide, el handler llama:

```text
0x01B8A1AC -> 0x027ABFE0
```

`0x027ABFE0`:

1. comprueba `GameMode::Coop` mediante `0x01C076CF`;
2. resuelve al otro actor;
3. valida ese actor;
4. obtiene su pack mediante `0x01BCC327 -> 0x01D336A0 -> actor+0x1524`;
5. invoca la virtual `cBioItemPack +0x34` para añadir la cantidad calculada.

El multiplicador usado en esa cantidad procede de:

```text
0x01B8D7F8 -> 0x02506FE0
```

Valores verificados directamente en el EXE:

```text
0x04CB87DC = 1.0f   ; valor base
0x05479970 = 1.5f   ; valor usado si GameMode::Coop
```

Por tanto hay dos problemas diferentes:

- **pickup principal:** entregar el item al actor que lo recoge; ya es actor-específico, pero Sub0 queda bloqueado por el gate `pl`;
- **ammo relief Coop:** bonificación/reparto adicional hacia el otro actor, activada sólo por `GameMode::Coop`.

Para cooperativo local, ambos deben resolverse de forma mínima e independiente; no se debe cambiar `mGameMode` global para desbloquearlos.


## 6. El finder stock tampoco puede elegir Sub0

El update común de `uItem` empieza la selección de actor en:

```text
0x0246213F..0x0246215E
```

Flujo verificado:

```asm
0x0246213F  call 0x01B95665
0x02462146  call 0x01C85962   ; identidad local
...
0x02462152  call 0x01B95665
0x02462159  call 0x01C07341   ; thunk -> 0x02DA3840
```

En `0x02DA3840` se itera la colección de actores. Antes de comparar la identidad:

```asm
0x02DA3898  call 0x01C8C9A1  ; is category pl
0x02DA38A3  cmp  ecx,1
0x02DA38A6  jne  siguiente
```

Solo un actor `pl` puede alcanzar la comparación con la identidad local.

El candidato devuelto se guarda en stack como `[ebp-0x2C]`, pasa las comprobaciones stock de distancia/estado y termina almacenado en:

```asm
0x024626B0  mov ecx,[ebp-0x2C]
0x024626B3  mov [eax+0xF48],ecx
```

Por tanto `uItem+0xF48` es el candidato local de pickup y, en stock PC, queda deliberadamente limitado al `pl` local.

### Consecuencia

Un parche correcto necesita al menos:

1. conservar el candidato P1 stock;
2. cuando `gLocalCoopActive==1`, considerar también el puntero exacto `gSub0Npc`;
3. usar la misma posición del actor (`actor+0x40`) y la misma posición del item (virtual `+0x60`, transform `+0x30`) para escoger al candidato adecuado;
4. no habilitar NPCs genéricos;
5. mantener los gates posteriores con la excepción exacta Sub0.

Parchear únicamente `0x02464733` no basta, porque Sub0 nunca llegaría a `uItem+0xF48` por la selección stock.


## 7. La finalización de uItem repite el gate pl

La función de finalización:

```text
0x02460610
```

empieza con:

```asm
0x02460645  mov eax,[this]
0x02460648  cmp dword ptr [eax+0xF48],0
0x0246064F  je  0x02460B64

0x02460655  mov eax,[this]
0x02460658  mov ecx,[eax+0xF48]
0x0246065E  call 0x01C53859
0x02460663  push eax
0x02460664  call 0x01C8C9A1
0x02460671  je  0x02460B64
```

Por tanto el candidato guardado en `uItem+0xF48` vuelve a ser rechazado si no es categoría `pl`.

Una vez superado ese gate, el actor se conserva en `[ebp-0x14]` y varias ramas terminan llamando:

```text
0x01C639B6 -> 0x024646F0
```

El helper `0x024646F0` vuelve a aplicar el mismo predicate `pl` antes de operar sobre el pack del actor.

### Tres bloqueos exactos demostrados

1. **selección:** `0x02DA3840` sólo devuelve el `pl` local;
2. **finalización uItem:** `0x02460664` rechaza cualquier candidato no `pl`;
3. **helper de entrega:** `0x02464726` vuelve a rechazar cualquier actor no `pl`.

Después de esos filtros, el almacenamiento sí es actor-específico mediante `uNpc+0x1524 -> cBioItemPack`.

La corrección local debe por tanto ser quirúrgica y limitada a estos puntos, aceptando solo:

```text
stock_is_pl(actor)
OR
(gLocalCoopActive == 1 && actor == gSub0Npc)
```

No debe alterar globalmente el predicate `isPlayer`.


## 8. Después de v11, el ActionCommand de uItem seguía anclado al pad 0

La función stock:

```text
0x026D7AD0
```

termina simplemente con:

```asm
xor eax,eax
ret 4
```

Por tanto su selector/member siempre es 0.

En paralelo, la API de `sGamePad`:

```text
0x02DB2B50
```

recibe un argumento (termina con `ret 4`), pero stock PC ignora ese argumento en:

```asm
0x02DB2B7D  mov ecx,[eax+0x970]
```

usando `mStartPadNo` global.

### Corrección v12 verificada

El binario v12 tiene SHA-256:

```text
5aafc3fd4273d608b4c9b8b60631256b56cb27d6aab0ecca8d2718d824dd28e8
```

En `0x026D7AD0`:

```asm
cmp dword ptr [gLocalCoopActive],0
je  return0
mov eax,[ecx+0xF48]
cmp eax,[gSub0Npc]
jne return0
mov eax,1
ret 4
return0:
xor eax,eax
ret 4
```

En `0x02DB2B7D`:

```asm
mov ecx,[ebp+8]
nop
nop
nop
```

Así el selector del ActionCommand queda:

```text
uItem target P1   -> member 0 -> PadData[0]
uItem target Sub0 -> member 1 -> PadData[1]
```

La modificación sólo se activa para el Sub0 exacto durante cooperativo local; los demás casos conservan selector 0.

## 9. Estado recuperado desde el punto del corte

Partiendo estrictamente de `0x049A8023`, ya se han revalidado directamente sobre el EXE original:

- `0x049A8023` = registro DTI de `uItem`;
- la entrega real usa `actor+0x1524 -> cBioItemPack`;
- el helper stock rechaza Sub0 por ser `np`;
- el finder stock sólo selecciona el `pl` local;
- `uItem+0xF48` es el candidato de pickup;
- la finalización repite el gate `pl`;
- v11 corrige selección + gates sólo para Sub0 exacto;
- v12 hace que el ActionCommand de ese pickup use el selector/pad 1;
- la rama `0x027ABFE0` es una regla secundaria de reparto de munición Coop y no debe confundirse con la entrega principal.

El siguiente bloque lógico es estudiar/aplicar esa regla secundaria de munición para local-coop sin cambiar `mGameMode` global, manteniendo la entrega genérica de otros objetos en el `cBioItemPack` del actor que los recoge.


## 10. v13: ammo relief local sin cambiar mGameMode

La versión verificada:

```text
BioRevHD 30-Enero-2013 LOCAL COOP v13 SYMMETRIC AMMO RELIEF.exe
SHA-256 3df0e1020b58b3ccc7e31a9046a2a3ce9e5230e1764869b517943b4a808838aa
```

parte exactamente de v12:

```text
5aafc3fd4273d608b4c9b8b60631256b56cb27d6aab0ecca8d2718d824dd28e8
```

y cambia:

```text
202 bytes
5 rangos
mismo tamaño PE
```

Helper en `0x01C95220`:

- conserva el resultado stock de `GameMode::Coop`;
- si stock no está en Coop, acepta `gLocalCoopActive`;
- para P1 selecciona el Sub0 exacto como otro actor;
- para Sub0 resuelve el P1 local como otro actor;
- conserva la validación stock y añade `pl` sólo en la dirección recíproca necesaria;
- cuando local-coop está activo usa el multiplicador Coop real `1.5f` de `0x05479970`;
- cuando local-coop está apagado vuelve a las funciones stock.

Hooks concretos de `0x027ABFE0`:

```text
0x027AC016 -> coop_or_local
0x027AC059 -> select_relief_other
0x027AC077 -> valid_relief_other
0x027AC0E2 -> ammo_multiplier_local
```

No se modifica `cSystemData<Game>::mGameMode`.

## 11. Hierbas: almacenamiento por actor ya presente

El metadata de `cBioItemPack` registra literalmente:

```text
mHerbNum
```

String VA:

```text
0x04D2D4C0
```

Registro:

```asm
0x0242D88D  add eax,0xC8
0x0242D893  push 0x04D2D4C0  ; "mHerbNum"
```

Por tanto:

```text
cBioItemPack + 0xC8 = mHerbNum
```

Dado que la entrega genérica ya se ha demostrado como:

```text
actor seleccionado
 -> actor+0x1524
 -> cBioItemPack propio
 -> operación de addItem
```

no se justifica crear almacenamiento separado de hierbas para P2. La lógica de pickup debe seguir usando el pack propio del actor.

En el handler analizado, la rama cooperativa adicional identificada es la de grupo `0x80040200` para ammo relief; no se ha encontrado una razón para cambiar globalmente la entrega genérica de otros objetos.
